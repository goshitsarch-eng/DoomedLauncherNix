# Engine compatibility

Doom Launcher starts your installed source port; it bundles no engine or game
data. The table describes the launcher's current integrations. **Only Chocolate
Doom 3.1.1 and Crispy Doom 7.1.0 have completed the real Linux engine checks
below.** Source inspection and automated argument/parser tests provide narrower
evidence for the other ports. An engine name does not establish compatibility
with every version, mod, save format or operating system.

| Source port | Automatic save directory and latest-save loading | Record/replay | Per-level statistics | Evidence |
| --- | --- | --- | --- | --- |
| Chocolate Doom 3.1.1 | `-savedir`; newest `doomsavN.dsg` loads with numeric `-loadgame N` | Verified | `-statdump` output verified | Real Linux engine checks |
| Crispy Doom 7.1.0 | `-savedir`; newest `doomsavN.dsg` loads with numeric `-loadgame N` | Verified | `-levelstat` output verified | Real Linux engine checks |
| Modern GZDoom, UZDoom, VkDoom | `-savedir`; newest `.zds` loads by filename relative to that directory | Standard demo arguments | Reads supported statistics from new or changed JSON-based `.zds` saves | Upstream save contracts and automated tests; binaries untested |
| Released LZDoom 3.88b, ZDoom, Zandronum | `-savedir`; newest `.zds` passed as a full filename | Standard demo arguments | Only compatible JSON-based `.zds` saves; older save formats may provide no statistics | Legacy path contract and automated tests; binaries untested |
| dsda-doom, PrBoom-Plus | `-save`; newest compatible numbered `.dsg` loads by numeric slot | Standard demo arguments | Requests `-levelstat` | Upstream save contracts and automated tests; binaries untested |
| Woof, Nugget Doom | `-save`; numbered normal saves or `autosave.dsg` load by numeric slot | Standard demo arguments | Requests `-levelstat` | Upstream save contracts and automated tests; binaries untested |
| Eternity | `-save`; newest `etersavN.dsg` loads by numeric slot | Standard demo arguments | No automatic level-statistics integration | Upstream save contract and automated tests; binary untested |
| Other ports or custom wrappers | Automatic latest-save loading unavailable unless the configured executable identifies a supported family | Conventional arguments in normal mode; use custom parameters when required | Depends on recognized executable; otherwise play time only | Configure and verify your engine's own contract |
| Doom 64 rerelease | Engine manages its saves | Engine manages demos | Play time only | Custom-parameter launch integration; binary untested |

“Standard demo arguments” means `-record <name>` and `-playdemo <file>` are
generated by the launcher; it does not mean that binary has been exercised.
Recordings are stored as associated `.lmp` files under `GameFiles/Demos`.
Replay requires the correct engine version, IWAD, mods and compatibility
settings for that recording. Load latest save cannot be combined with demo
recording or playback. Finish recording through the engine before stopping it
if you want a complete demo.

## Where saves go

For recognized ports, normal launches use
`<library>/GameFiles/SaveGames/<entry ID>/<source-port ID>/`. An alternative save
directory configured on a source port replaces the root; the same two ID
subdirectories are still added. The launcher creates the directory before
starting the engine. Entries and source ports therefore do not share the same
automatic save search.

Existing saves in an engine's old directory are left untouched. They are not
moved, deleted or searched globally. To reuse one, copy a compatible save into
the entry's managed directory with its original filename, or use the engine's
own load controls and documented custom arguments. Attaching a save to a
library entry does not automatically place it in this per-port directory.

Load latest save selects the newest modification time among compatible files
in that entry's directory. If none exists, the launcher asks you to save once
or disable the option. dsda-doom accepts slots 0–118; PrBoom-Plus supports its
numeric slot contract. Their default prefixes are `dsda-doom-savegame` and
`prboom-plus-savegame`; BEX overrides are accepted, while demo saves are
excluded. Woof/Nugget support their normal page/slot saves and `autosave.dsg`
(slot 255); quicksave and periodic-autosave filenames are excluded when they
cannot be loaded through that numeric contract.

Port identification uses the configured executable name or package identifier.
Unrecognized wrappers and older builds with different arguments should use
**Extra parameters only** and the engine's documentation. That mode leaves
automatic game, save, demo and statistics arguments out of the launch. Inspect
the command preview before starting. In particular, modern GZDoom's relative
save-name handling differs from older ZDoom-derived builds. Custom multiplayer
parameters may also change where an engine stores saves.

## Statistics and tested behavior

Elapsed play time is tracked independently of level-statistics support.
Level statistics are collected after the session ends from output changed
during that session. For `-levelstat` ports, the default working directory is
`<library>/GameFiles/EngineData/<entry ID>/<source-port ID>/`. It persists across
launches, so manual screenshots, configuration and other files an engine writes
there survive automatic temporary-file cleanup (`CleanTemp`). Before the next statistics launch,
the previous `levelstat.txt` is preserved under `levelstat-history/<unique ID>.txt`
in that directory. Starting with a fresh output filename supports engines that
append as well as those that overwrite, without importing an older session twice.
Two active sessions cannot write the same statistics file.

A custom working directory distinct from the engine's installation directory
is retained and checked for write access. Outside managed `EngineData`, the
launcher leaves existing output files in place; custom engine versions may
require checking their overwrite/append behavior. For compatible ZDoom saves,
statistics require the engine to write a save containing the supported JSON fields.

Additional executable families retain the existing statistics selectors:
`crispy-heretic`, `so-doom`, `inter-heretic`, `boom-plus`, `nyan-doom`, `fdwl`
and `cherry-doom` request `-levelstat`; `cndoom`, `crl-doom` and `inter-doom`
request `-statdump`. These names have not received real-engine validation here,
and this selector alone does not enable automatic latest-save loading.

On 2026-10-09, Chocolate Doom **3.1.1** and Crispy Doom **7.1.0** ran on Linux
through the real Rust backend, under Xvfb in an Ubuntu container. Tests used
Freedoom **0.13.0** and an original generated MAP01, with audio disabled. Both
rendered gameplay, wrote a real save through the engine menu, reloaded it using
the launcher's latest-save option, completed the map, recorded and replayed a
demo, and responded to Stop. Demo associations and each engine's parsed level
statistics were confirmed in SQLite. Replay exited successfully. Their normal
demo-completion exit code 255 is recognized only with the expected completion
message and a saved demo; the original exit code remains in session details.

The final rerun used the packaged release Rust library and actual installed
engine binaries. Each engine completed a second map run, with exactly two
persisted statistics records; Crispy's prior statistics output remained in
`levelstat-history` after shutdown. See the [packaged-core QA record](QA.md#real-engine-checks-using-the-packaged-native-core)
for the exact artifact hash and captures.
They do not establish other engines, Windows/macOS, multiplayer, hardware
rendering, audio or every game-format variant. See [desktop QA](QA.md),
[platform support](../PLATFORM_SUPPORT.md) and [build/test instructions](../BUILDING.md)
for the separate launcher and packaging checks.
